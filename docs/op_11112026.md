## Manual Set-Up Sequence

### Step 4 -- Prepare the host for rootful k3d

k3s nodes inside containers need **shared mount propagation** on `/` so the
kubelet can bind-mount host paths into pod containers. The Podman API socket
directory also needs to exist (it lives on tmpfs, so it's gone after reboot).

```bash
# --- Action ---

# Make / shared so mounts propagate into nested containers (k3s nodes).
# Without this, the kubelet inside node containers can't bind-mount
# host paths into its own pod containers.
sudo mount --make-rshared /

# Persist across reboots -- runs at the end of boot before any services
# (Void's rc.local is executed by runit at the very end of the boot sequence)
echo 'mount --make-rshared /' | sudo tee -a /etc/rc.local

# Create the socket directory for the rootful Podman API.
# /run is a tmpfs, so this is recreated every boot. The runit service
# (set up in step 5) will also create it on start, but creating it here
# lets us verify permissions upfront.
sudo mkdir -p /run/podman

# --- Debug / Verify ---

# Confirm propagation is now "shared" (was "slave" before):
findmnt -no PROPAGATION /

# Check the rc.local line was persisted:
grep rshared /etc/rc.local

# Check /run/podman exists with correct ownership (root):
stat -c '%a %u %g %n' /run/podman
```

### Step 5 -- Start the rootful Podman API (runit service, Option A)

k3d only speaks the Docker API protocol. It doesn't have a native Podman
provider the way `kind` does. So we run Podman's Docker-compatible API socket
as an on-demand runit service. The API never owns the containers (`conmon`
does), so stopping the service doesn't affect a running cluster.

```bash
# --- Action ---

# Install the runit service from the repo's artifact
sudo mkdir -p /etc/sv/podman-api
sudo cp artifacts/podman-api.run /etc/sv/podman-api/run
sudo chmod +x /etc/sv/podman-api/run

# Create the "down" file so the service is supervised but does NOT start
# at boot -- it's started on demand by k3dctl or manually:
sudo touch /etc/sv/podman-api/down

# Enable the service by symlinking into /var/service (runit's service dir):
sudo ln -s /etc/sv/podman-api /var/service/

# --- Debug / Verify ---

# The run script exists and is executable:
ls -la /etc/sv/podman-api/run

# The symlink in the active service directory:
ls -la /var/service/podman-api

# Status should show "down" (not started) because of the "down" file:
sv status podman-api

# --- Action (start the API) ---

sudo sv up podman-api

# --- Debug / Verify ---

# Status should now say "run":
sv status podman-api

# Query the API to confirm it's alive -- should return JSON with version info:
sudo podman --remote --url unix:///run/podman/podman.sock info

# The socket file itself:
ls -la /run/podman/podman.sock

# If it fails, check the logs:
sudo cat /var/log/podman-api/current 2>/dev/null || echo "no svlogd -- check /etc/sv/podman-api for log/run"
```

### Step 6 -- Create the k3d cluster

The cluster is defined in `k3d.yaml` and runs as rootful Podman through the
API socket. Before creating, we remove any stale network from a previous
attempt -- container DNS (via `aardvark-dns`) is only properly configured at
network creation time.

```bash
# --- Debug: check what exists before we start ---

# List all Podman networks -- look for a stale k3d-lab:
sudo podman network ls

# List any leftover node containers from a previous run:
sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}}'

# Check ports from k3d.yaml are free:
sudo ss -tlnp | grep -E ':(8080|8443)\b' || echo "ports clear"

# --- Action ---

# Remove stale network so DNS is reconfigured fresh at creation time
sudo podman network rm k3d-lab 2>/dev/null || true

# Create the cluster -- k3d as root, pointed at the Podman API socket.
# DOCKER_HOST and DOCKER_SOCK are passed explicitly because sudo strips
# the environment.
sudo DOCKER_HOST="unix:///run/podman/podman.sock" \
     DOCKER_SOCK="/run/podman/podman.sock" \
     k3d cluster create --config k3d.yaml

# --- Debug / Verify ---

# Podman network should now exist with DNS configured:
sudo podman network ls | grep k3d-lab

# Inspect DNS -- if empty ( [{}] ), container DNS is broken:
sudo podman network inspect k3d-lab | jq '.[] | .dns'

# List node containers and their status (should be "up"):
sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}} {{.Ports}}'

# Check node IPs on the k3d-lab network:
sudo podman inspect k3d-lab-server-0 | jq '.[].NetworkSettings.Networks["k3d-lab"].IPAddress'

# Peek at k3s boot logs (useful if nodes are restart-looping):
sudo podman logs k3d-lab-server-0 2>/dev/null | tail -30
```

### Step 7 -- Hand over the kubeconfig & wait for Ready

k3d ran as root, so its kubeconfig lives in root's home. We copy it to the
normal user's `~/.kube/` so kubectl/helm/k9s work without sudo.

```bash
# --- Action ---

# Get the kubeconfig from k3d (still through the rootful API socket):
mkdir -p ~/.kube
sudo DOCKER_HOST="unix:///run/podman/podman.sock" \
     DOCKER_SOCK="/run/podman/podman.sock" \
     k3d kubeconfig get lab > ~/.kube/k3d-lab.yaml
chmod 600 ~/.kube/k3d-lab.yaml

# --- Debug / Verify ---

# The kubeconfig should be a valid YAML with server, CA, cert and key:
cat ~/.kube/k3d-lab.yaml

# Quick reachability test (no auth round-trip, just connection):
kubectl --kubeconfig ~/.kube/k3d-lab.yaml cluster-info

# --- Action (wait for Ready) ---

# Wait up to 3 minutes for all k3s nodes to reach Ready state.
# If this times out, check podman logs above (step 6 debug) for boot errors.
KUBECONFIG=~/.kube/k3d-lab.yaml kubectl wait --for=condition=Ready nodes --all --timeout=180s

# --- Debug / Verify ---

KUBECONFIG=~/.kube/k3d-lab.yaml kubectl get nodes -o wide

# Check what pods exist (should see the k3s controlplane components):
KUBECONFIG=~/.kube/k3d-lab.yaml kubectl get pods -A

# --- Shell integration (append k3d.bashrc to ~/.bashrc) ---
#
# This does three things:
#   1. Merges ~/.kube/k3d-*.yaml into KUBECONFIG so kubectl finds the
#      cluster automatically
#   2. Defines a `k3d` shell function that wraps sudo + DOCKER_HOST so
#      one-off commands like `k3d image import` work without k3dctl
#   3. Sets `k` as an alias for kubectl with completion
cat artifacts/k3d.bashrc >> ~/.bashrc
source ~/.bashrc

# Verify the integration:
echo "$KUBECONFIG"                # should include :/home/mii/.kube/k3d-lab.yaml
kubectl cluster-info               # works without --kubeconfig
k cluster-info                     # alias works
```

## Teardown Sequence

### Stop cluster (keep data, free CPU/RAM)

Stopping the cluster pauses the node containers so they don't consume CPU/RAM.
The API must be alive to send the stop command to the cluster. Once stopped,
the API is shut down too.

```bash
# --- Debug: current state ---

sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}}'
KUBECONFIG=~/.kube/k3d-lab.yaml kubectl get nodes 2>/dev/null || echo "cluster already unreachable"

# --- Action ---

# Start the API if it isn't already running:
sudo sv up podman-api
sv status podman-api                # should show "run"

# Stop the cluster through the API:
sudo DOCKER_HOST="unix:///run/podman/podman.sock" \
     DOCKER_SOCK="/run/podman/podman.sock" \
     k3d cluster stop lab

# --- Debug / Verify ---

# Containers should now show "exited" instead of "up":
sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}}'

# --- Action ---

# Stop the API -- containers keep running (conmon owns them, not the API):
sudo sv down podman-api

# --- Debug ---

sv status podman-api                # should say "down"
# API socket should be unreachable:
sudo podman --remote --url unix:///run/podman/podman.sock info 2>&1
# -> "cannot connect" or connection refused
```

### Delete cluster (nuke everything)

Deletes the node containers, the k3d cluster metadata, the Podman network,
and the local kubeconfig.

```bash
# --- Debug: what we're about to delete ---

sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}}'
sudo podman network ls | grep k3d-lab
ls -la ~/.kube/k3d-lab.yaml

# --- Action ---

# API must be alive to talk to the cluster:
sudo sv up podman-api

# Delete the cluster:
sudo DOCKER_HOST="unix:///run/podman/podman.sock" \
     DOCKER_SOCK="/run/podman/podman.sock" \
     k3d cluster delete lab

# Remove the Podman network:
sudo podman network rm k3d-lab 2>/dev/null || true

# Remove the local kubeconfig:
rm -f ~/.kube/k3d-lab.yaml

# Stop the API:
sudo sv down podman-api

# --- Debug / Verify ---

# No containers left:
sudo podman ps -a --filter "name=k3d-lab" --format 'table {{.Names}} {{.Status}}'
# -> empty

# No network left:
sudo podman network ls | grep k3d-lab
# -> empty

# No kubeconfig left:
ls ~/.kube/k3d-lab.yaml 2>&1
# -> "No such file or directory"

# Update KUBECONFIG in current shell (new shells will pick it up from bashrc):
export KUBECONFIG=$(echo ~/.kube/config; for f in ~/.kube/k3d-*.yaml; do [[ -e $f ]] && echo ":$f"; done | tr -d '\n')
echo "$KUBECONFIG"                 # should no longer include k3d-lab.yaml
```

### Full host reclamation

Reverts everything step 4 set up: removes the runit service, the rshared
mount, the rc.local line, and the socket directory. Only needed if you want
to completely undo the rootful Podman setup.

```bash
# --- Debug: what we're about to remove ---

ls -la /var/service/podman-api 2>/dev/null
ls -la /etc/sv/podman-api 2>/dev/null
findmnt -no PROPAGATION /
grep rshared /etc/rc.local

# --- Action ---

# Remove the runit service:
sudo rm /var/service/podman-api
sudo rm -rf /etc/sv/podman-api

# Restore default (slave) mount propagation on /:
sudo mount --make-rslave /

# Remove the rc.local persistence line:
sudo sed -i '/mount --make-rshared \//d' /etc/rc.local

# Remove the socket directory:
sudo rmdir /run/podman 2>/dev/null || true

# --- Debug / Verify ---

findmnt -no PROPAGATION /          # should say "slave" (or show nothing)
grep rshared /etc/rc.local         # -> no output
sv status podman-api 2>&1          # -> "service unavailable" or similar
ls -la /run/podman 2>&1            # -> "No such file or directory"
```

## Results - What We Tried and What Broke

### Attempt 1: Rootful k3d via Docker API socket

Setup:
- Created runit service `/etc/sv/podman-api` for the rootful Podman API socket
- Symlinked `/var/run/docker.sock -> /run/podman/podman.sock` so k3d finds the socket
  at the default path
- Ran k3d with `DOCKER_HOST` pointing at the socket

Outcome:
- [OK] Network created
- [OK] Image volume created
- [OK] Tools container ran, gathered env info
- [OK] Server-0 started and reported `k3s is up and running` (~6s)
- [OK] Agent-0 registered with the server (~10s)
- [FAIL] **Agent-1 never registered** -- k3d hung waiting for it

Root cause: DNS resolution broken inside containers.
The Podman network (`k3d-lab`) was created through the Docker API
compatibility layer, which set `dns_enabled: true` but left `dns: null`.
Without a DNS server address, `aardvark-dns` couldn't serve hostname
resolution. Agent containers couldn't resolve `k3d-lab-server-0` to
register with the cluster.

```bash
# Confirmed:
sudo podman exec k3d-lab-agent-1 ping -c1 k3d-lab-server-0
# -> ping: bad address 'k3d-lab-server-0'

sudo podman network inspect k3d-lab | jq '.[0].dns'
# -> null
```

Workaround identified (not executed):
Create the network manually with native `podman network create --dns`
before running k3d, so DNS is properly configured. k3d would detect the
existing network and reuse it.


### Attempt 2: Rootless k3d (isolate the cgroup blocker)

Setup:
- Started rootless `podman system service` on `$XDG_RUNTIME_DIR/podman/`
- Pulled k3s image into rootless store
- Ran k3d with `DOCKER_HOST` pointing at the user socket

Outcome:
- [OK] Network, volume, tools container all created
- [FAIL] Server-0 exited immediately - could not start k3s

Root cause: No cgroup v2 delegation for non-root users.
The k3d entrypoint's cgroup fix script (`/bin/k3d-entrypoint-cgroupv2.sh`)
tried to create `/sys/fs/cgroup/init` and got `Permission denied`.
Without systemd's `user@.service` (not available on Void/runit), there's
no user-owned cgroup tree to delegate to.

```bash
# From the container's /var/log entrypoint logs:
mkdir: cannot create directory '/sys/fs/cgroup/init': Permission denied
```

Verdict: Rootless k3d is impossible on this host without cgroup delegation.


### Pivot: Switching to `kind`

k3d has no native Podman provider -- it always goes through the Docker
API compatibility socket. Every issue we hit (DNS, loadbalancer config)
traces back to this translation layer not handling Podman's semantics
correctly. (The cgroup issue is a separate host-level limitation.)

`kind` has a **native Podman provider** and does not need the API socket
at all. It speaks Podman directly:
- [OK] Container DNS -- networks created natively
- [OK] No loadbalancer config volume issues
- [OK] No `podman system service` needed
- [OK] No sudo for basic operations

Tradeoff: kind runs upstream Kubernetes (kubeadm) instead of k3s
(Rancher's minimal distro). Same kubectl, same manifests, different
cluster lifecycle tool.
